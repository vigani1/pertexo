# Persisted identifier ownership

Application-owned entity, event, version, attempt, intent, idempotency-row, and
artifact identifiers use UUIDv7. The database package owns one
`generatePersistedId()` implementation and exposes it through
`@pertexo/database/platform`. Database stores use the same implementation
internally. Its regression tests verify UUID version, uniqueness, monotonic
lexical order, and artifact persistence.

UUIDv4 remains intentional for values whose security or concurrency semantics
are random rather than sortable:

- inbound request and trace correlation fallbacks;
- dispatcher, schedule, retention, purge, and lifecycle lease tokens;
- connection-test dispatch capability tokens;
- generated idempotency-key material that is immediately hashed; and
- external exercise request identifiers.

Database functions sometimes create a persisted ID with `gen_random_uuid()`
inside one atomic SQL transition. These are not column defaults and cannot be
pre-generated by an application without widening a function contract. They are
retained for the SQL-owned claim, fold and recovery transitions; their ordering is
never used. New application write paths must use
`generatePersistedId()`, while a new SQL-owned exception requires migration
review and a statement of why its identity must be allocated inside the atomic
operation.

`pnpm database:schema:check` rejects UUID-generating column defaults and
requires every `app` table created by migrations to have a Drizzle definition
under `packages/database/src/schema/`.
