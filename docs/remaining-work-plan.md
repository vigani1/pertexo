## Priority and completion rules

**P1**: protect secret handling, execution/cancellation correctness, or a claimed
release gate. **P2**: close a deterministic evidence gap or clarify real ownership.
**P3**: conditional maintainability work with a demonstrated benefit, not a quota.
**External**: required production evidence, gated by specific authorization.

Every implementation task must have: a public behavior or existing adapter test
surface, assertions beyond “does not throw,” an exact command/result record,
review of the changed diff, and a fresh owning coverage report where relevant.
For a targeted branch, completion means the exact branch is hit in a current
report, or a reviewed invariant explains why it must remain unexecuted. A sibling
case, a stale branch ID, and an ordinary success test are insufficient substitutes.

Do not mutate branded execution state just to increase coverage. Serialized
untrusted checkpoint input is different: when a public decoder accepts unknown
data, malformed serialized input is a legitimate test surface. Do not remove
runtime guards, expose private functions, weaken types, or lower thresholds to
make a report green.

### O01 — Sanitize queue-span exception recording (P1, confirmed local path)

Files: `packages/observability/src/queue-tracing.ts`,
`telemetry-sanitization.ts`, and `test/queue-tracing.test.ts`.

At the queue trace catch path, `span.recordException` receives the original
`Error`, including arbitrary message/stack content. The existing failure test
asserts that same raw object. HTTP spans have sanitization, but it is installed
through HTTP instrumentation hooks; the queue-created span does not receive it.
The local collector only drops process resource attributes, not exception text.
A synthetic-marker probe through `createQueueTraceRunner` confirmed that the raw
marker-bearing Error is recorded and the original error is rethrown. This proves
the recording path, not an observed production credential leak.

Action: record a bounded, safe exception classification on the queue span while
preserving the original thrown error for control flow. Reuse an appropriate
package-internal sanitizer only if it has safe behavior for this input surface;
do not blindly expose the HTTP hook or introduce a new public contract.

Acceptance: synthetic secrets in message, stack, cause, custom name/code and
non-Error throws never appear in recorded/exported queue spans; no hostile
getter executes; safe classification and ERROR status remain; `span.end()` runs
exactly once; original rejection identity survives. Include a real in-memory
span exporter test, not just a mocked recordException assertion. Check adjacent
enabled instrumentation with synthetic failures as O02, not an unsupported
claim that HTTP redaction covers every instrumentation. The implemented check
covers Nest and PG wrappers with an in-memory exporter. The pinned ioredis
instrumentation supports only ioredis `<6`, so it was removed from the ioredis
6 runtime instead of being represented by an inapplicable v5 test; Redis
continues to emit bounded queue-owned metrics inside the sanitized queue span.

Before any exercise, name: account/environment/regions; exact release commit and
image digests; contract and migration versions; isolated resource selectors and
synthetic tenants; providers and recipient allowlists; exercise window; request,
cost, concurrency, and duration caps; operator and independent approver; evidence
destination/access/retention; stop conditions; rollback/failback owner. Resolve
every required field in the canonical E01 packet. “AWS access available” or
“run everything” is not a substitute for scoped destructive-action approval.

### X01 — Supply chain and repository controls (external / conditional)

Select and verify registry/signing identities, signed provenance, SBOM and image
vulnerability scan tied to the exact digest, and independent promotion checks.
Verify required CI/security/CodeQL checks and branch protection through approved
repository access. Exercise push protection and dependency/image gates with
approved synthetic canaries, not real secrets or malicious customer branches.
An independent code owner/second maintainer requires an actual person; retain
the documented solo-maintainer exception with owner/expiry until then. Do not
claim a second reviewer was simulated by another AI agent.

### X02 — Final release qualification and recording

After authorized local fixes, run narrow checks at coherent boundaries, then the
complete local qualification on the exact final tree. Review all skipped tests
by name. If commits are authorized, stage only the logical owned change, inspect
the staged diff, commit passing work, and report hashes. Before an authorized
push, fetch and verify upstream is neither ahead nor diverged. A fresh protected
CI/security result on the exact release commit and all required external
receipts—not this plan—are the final release evidence.

## Sequencing and ownership

1. **Evidence/security first:** O01, G01, R01. These are narrow, concrete and do
   not depend on external credentials. Confirm W01's effective budget in parallel.
2. **Execution lifetime:** W01/W02 after contract review and reproductions;
   shared database/worker lifetime decisions stay with one integrator.
3. **Deterministic test closure:** I01/I02, F02/F04, and the appendix's actionable
   app/database families. Preserve exact branch identity and public assertions.
4. **Measurement:** G02/G03 with Q01/D02/F03; do not duplicate existing tests.
   Reclassify new rows before tightening any newly introduced thresholds.
5. **Ownership and conditional depth:** D01, then H01 only if its comparison
   justifies change. Preserve M06/M07/M08 retentions unless new evidence defeats
   their recorded reasons.
6. **Fresh local qualification:** G04/X02; close only verified local tasks.
7. **External qualification:** E00, X01, then all applicable E01 scenarios and
   named DB/OBS/INT/ART evidence. Stop when the required authorization is missing.

Safe parallel ownership: observability; quality reporter; integration tests;
workflow/SDK tests; database evidence. Do not give multiple writers the shared
risk-review JSON or cross-package cancellation contract simultaneously.

## Deliberate retentions and scope boundaries

- M01–M05 are done; M06 feature composition, M07 dispatcher capacity locality,
  and M08 workflow decision/mutation locality retain their documented decisions.
- Keep guards justified by validated record bounds, AES-GCM invariants,
  canonical unique keys, supported Node-only exports, validated array indices,
  and source-less instrumentation positions. The appendices identify exact rows.
- **C-23:** keep the current 30-file/33-function complexity ratchet and the
  owner-specific retention ledger. Historical 35/40 counts are not today's
  inventory and do not require another blanket split.
- **C-24:** continuous assurance maps to G02/G03/G04, not an arbitrary 100% goal.
  **C-25:** keep immutability/optional-property ownership policy; remove freezes,
  copies or validation only after mutation characterization or profiling proves
  the proposed change safe and useful. No such removal is authorized here.
  **C-27:** conditional type-aware infrastructure work maps to H01. Completed
  C-21/C-22/C-26/C-28 and earlier code fixes remain closed unless contradicted.
- **ART-011:** preserve unbundled SDK command identity and actual image/export
  checks. **INT-009:** keep the pinned IANA-registry drift check and explicit
  upstream refresh/review process; do not silently change the address policy.
  **DB-016:** run deployed checksum/constraint retirement inventories at the
  documented review or before retirement; published migrations remain immutable.
- Do not reopen settled database authority, RLS, Redis non-authority, execution
  checkpoints, provider ambiguity, two-region ledger, or forward-only migration
  decisions without a concrete contradiction and a separately approved ADR.
- No new frontend, provider catalog expansion, new workflow semantics, generic
  infrastructure framework, arbitrary repository-wide rewrites, or score target.
- The currently unused preview artifact-producing executor path is a retained
  capability/evidence limitation, not permission to invent a new executor.
  If a supported executor must emit preview artifacts under ADR 016, prove its
  actual consumer and retention path as a separate vertical slice. Likewise,
  membership/invitation mutations and multi-node previews are not added by a
  code-quality review.
- A later audit can discover additional work. That possibility is not a license
  to label an unexamined path safe or to invent a defect now.
