# Files in workflows

Upload a file once and use its finalized workspace reference in **Read file**,
a raw **HTTP Request** body, an HTTP multipart part or a **Send email**
attachment. **Create file** produces
the same reference from step data. Both steps handle JSON, CSV and Excel
workbooks (`.xlsx`); Create file also writes plain text. A reference can also come from manual run
input or an earlier HTTP response. File bytes stay in the
existing artifact store; the editor does not parse files or save signed URLs.

## Create a file from data

Add **Create file** and map its **Data** input from an earlier step:

- **CSV:** a list of objects. A header is always included. Leave Columns empty
  to discover fields across the rows, or enter one field name per line in the
  exact output order. Column selection shares the existing 4,998-item cap and
  whole-value bounds. Choose comma, semicolon or tab. Missing and null
  cells are empty; objects and lists inside cells use compact JSON.
- **Excel:** the same list of objects and the same column choice as CSV,
  written as one sheet (named **Sheet1** unless you change the tab). The header
  row is bold and frozen. Numbers stay numbers, `true`/`false` become Excel
  booleans, and everything else is text; objects and lists inside cells use
  compact JSON. No cell is ever written as a formula.
- **JSON:** any value within the usual step-data bounds, written as compact JSON.
- **Plain text:** a string, written exactly as UTF-8 without an added newline.

For example, map `[{"currency":"EUR","amount":20},{"currency":"USD","amount":9}]`
to Data and choose the CSV columns `currency`, then `amount`. The result is:

```csv
"currency","amount"
"EUR","20"
"USD","9"
```

CSV fields are quoted, embedded quotes are doubled and records use CRLF.
Text cells and headers that could be spreadsheet formulas receive a leading
apostrophe, as table and audit exports do. That apostrophe remains part of the
text if another step reads it back. Use JSON when exact value types matter.

In Excel, text that starts with `=`, `+`, `-` or `@` is stored as text with
Excel's own quote prefix, so it shows as written and stays text even after
someone edits the cell; reading it back gives the exact text, with no added
apostrophe. Cells hold up to 32,767 characters, Excel's limit.

In the editor, **Setup → Columns, in output order** is a list: add a field
name (or paste several, one per line), move columns up or down, or remove
them. For Excel, a small sheet below shows the bold header and the first row of
a literal Data mapping, with the sheet's name on its tab.

The output's **file** field is a finalized reference. Map it to **Read file →
File**, or to an **HTTP Request** multipart file part. For an API expecting a
`report` upload, choose a file part named `report`, set its filename to
`report.csv`, and map Create file's `file` output as its value. Creating a file
calls no destination; sending it uses the normal HTTP effects acknowledgement.
A file close to 10 MB still needs room for multipart framing.

The 4,998-item collection ceiling and whole invocation envelope both apply:
about 4,996 narrow object rows fit Create file with automatic columns; wide
rows or many explicit column names fit fewer. Use **Batch items → For each →
Create file** for larger lists, then send each file separately. Files retain
the existing run/test/preview lifetime, workspace access and storage accounting.
No file contents appear in failure diagnostics. Fix the input, choose fewer
columns or split the data when the step reports that a file cannot fit.

## Limits before you start

| Operation             | Limit                                                                     | When it is too large                                                 |
| --------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Create file (inline) | 1 MB, including CSV headers and quoting | Choose From pages, fewer columns or split the data |
| Create file (from pages) | 10 MB of generated bytes | Choose fewer columns or split the data |
| Read file (inline)    | 1 MB of file bytes                                                        | Split the file and upload/run the pieces separately                  |
| Excel workbook | 1,000 archive parts, 100 MB uncompressed, 256 sheets, 1,000,000 cells read per step | Delete unused sheets or split the rows into smaller workbooks |
| Lists after Read file | About 4,996 narrow CSV rows end to end; fewer for wide rows               | Split by rows or reduce the columns before uploading                 |
| Raw HTTP file body    | 10 MB of file bytes (or lower configured storage limit)                                                        | Send a smaller file or separate uploads supported by the destination |
| Multipart HTTP body   | 10 MB **including every part header and boundary**, up to 64 ordered parts | Use smaller files; a full 10 MB file cannot fit with framing          |
| Email attachments     | 10 files and 6 MB together (8 MB once base64-encoded)                      | Attach fewer or smaller files, or split them across several emails    |

The UI uses binary units: 1 MB means **1 MiB (1,048,576 bytes)**; 10 MB is **10 MiB (10,485,760 bytes)**. A lower configured storage ceiling wins. Each parsed array accepts up to
4,998 items; downstream list wrappers leave roughly 4,996 narrow rows.
Every inline parsed result must fit the existing 1 MiB JSON value envelope,
depth 64 and 10,000-member limit. Retained run/preview values and checkpoints
also keep their smaller 256 KiB bounds; pages keep larger bytes outside those
values. Wide or expanded records can hit these bounds
sooner; the row estimate is not an additional quota. A stored file or HTTP
response larger than these consumer limits cannot be used merely because it
uploaded successfully.

Files use verified private worker disk scratch, not a whole-file worker buffer. Length and SHA-256 must match through EOF before parsing or sending any bytes to a destination. Pertexo never silently truncates rows or expands the ordinary JSON/checkpoint limits. Split files above 10 MB; larger files remain later work.

## Work with larger data as explicit pages

In **Read file → Setup → Output**, choose **Output pages**. JSON must be a top-level array; CSV uses the same headers, quoting, BOM and conservative conversion rules as inline reading, and Excel the same sheet, header row and cell rules. The output is metadata, not a loaded array:

```json
{ "pages": ["ordinary finalized file references"], "itemCount": 2000, "pageCount": 2 }
```

The illustrative strings stand for the ordinary reference objects described below. Each file contains a UTF-8 JSON array, at most **64 KB**, **1,000 records**, depth **48** and **4,000 fields/items**, including framing. The whole result allows at most **10 MB**, **100,000 records** and **256 page files**. A wide record can cause more files; a single record must fit a page. Size errors ask you to split or narrow the source. All files must finalize before the step succeeds; malformed final bytes or a storage failure never return a successful partial bundle.

To consume the records, map `$.pages` to an outer **For each**. Inside it, map **Current item** to **Read file → File**, leaving Output as **Inline data**. Map that parsed array to **Filter items**, **Summarize items** or an inner **For each**. A currency export can be filtered and summarized once per page. Keep per-page results small. Ordinary collection, checkpoint and whole-run iteration/step budgets still apply: pages do not grant 100,000 individual step executions. Use page-level/bulk operations or separate runs for larger work. See [For each](for-each.md#work-with-file-pages).

To reassemble a file, choose **Create file → Data source → From pages** and map the ordered `$.pages` list to **Pages** (remove an incompatible Data mapping). JSON writes one array; CSV and Excel require explicit columns in output order and write one header. It reads one checked page at a time. The generated file must fit 10 MB including quoting and framing; CSV expansion may reach this limit before its input does. Plain text still takes inline Data.

HTTP pagination also offers [Save items as pages](http-requests.md#save-items-as-pages), with the same files and consumers. Run detail and single-step test output show record/file/byte counts and authorized downloads. No browser parsing or automatic lazy loading occurs.

Page references follow normal workspace access, physical storage accounting, pin/draft/version/run retention and purge. Copying a reference through export/import or promotion grants no access and copies no bytes. File-aware recovery stays deferred.

## Upload from the editor or run input

Read file's **Inputs → Upload file to read** inserts a finalized `file` mapping.
HTTP's raw mode has **Upload body file**; multipart file parts have **Upload part
file**. Wait for **File ready**, then explicitly use the file. Inserting it is
one undoable edit; replacing a mapping does not erase shared bytes. Save before
relying on retention.

For a different file on each run, choose **Run → Run with input… → Upload file**.
Pick a top-level property (`file` by default). Existing JSON properties stay;
replacing a property requires its checkbox. Input must be an object and fit any
published callable input contract. Map the step's file value from **Run input**,
path `$.file`.

The live thread shows checking, upload and verification phases without an invented
percentage. Cancel or leaving the workflow, person or workspace aborts local
work and prevents late attachment. Changing a multipart part or its value also
fences pending insertion. **Check and retry same file** reconciles the original
reservation, key and metadata. Expired reservations need a fresh selection;
reloading abandons the local selection. Browser File objects stay transient.

Uploads go directly to the configured store without application credentials.
The server needs `ARTIFACT_STORE_*` configuration and bucket PUT CORS for the web
origin. Unavailable storage is reported as configuration, not a changed role.

## Read JSON or CSV into data

Add **Read file** under the data steps and select JSON or CSV in Setup (Excel
has [its own section](#read-excel-workbooks)). Map `file`
from an uploaded literal reference, run input `$.file`, or a preceding HTTP
Request's `$.body` when that response is a file. The worker reads the complete
checked file in the same workspace before parsing it. Neither MIME type nor
filename chooses the format.

JSON returns the parsed value directly. For `{"orders":[{"amount":12.5}]}`, a
following list step maps **Step output → Read file → `$.orders`**. For an array
such as `[{"amount":12.5}]`, map `$`. Parsing rejects malformed JSON, invalid
UTF-8, non-finite numbers and results over the value bounds; it does not coerce
JSON strings into numbers. Repeated JSON object keys follow standard JSON
semantics: the last value wins.

CSV returns an array of objects keyed by the header row. Choose comma, semicolon
or tab explicitly. UTF-8 and one initial BOM are supported, including quoted
delimiters, escaped double quotes and multiline quoted cells (RFC 4180 quoting).
Headers must be nonblank and unique, and every record must have the same number
of columns. Cells and headers are not trimmed. Completely blank lines outside
quotes are skipped; empty quoted cells are kept. A whitespace-only line is a
record, not a blank line.

**Convert numbers and booleans** defaults on. Conversion recognizes exact
lowercase `true`/`false` and JSON decimal number syntax that yields a finite
JavaScript number; integral values must be safe integers. For example:

| CSV cell                                              | Output with conversion on |
| ----------------------------------------------------- | ------------------------- |
| `12.5`, `-2`, `1e3`                                   | Numbers                   |
| `true`, `false`                                       | Booleans                  |
| `00123`, `9007199254740993`, `1e400`                  | Strings                   |
| Empty cell, `null`, `TRUE`, `" 12 "`, dates/currency text | Strings, unchanged        |

Quoting changes CSV syntax, not conversion: `"12.5"` also becomes a number.
Turn conversion off to keep every cell as text, such as an export of numeric
identifiers.

### Example: summarize a CSV export by currency

Upload this UTF-8 export to Read file, leave conversion on, then link:

**Read file → Filter items → Summarize items → Stop run**

```csv
currency,amount,paid
EUR,12.5,true
EUR,7.5,true
USD,9,true
EUR,100,false
```

1. Read file: CSV, comma delimiter, conversion on.
2. Filter items: map `items` from Read file `$`; path `$.paid`, operator equals,
   comparison value boolean `true`.
3. Summarize items: map `items` from Filter items `$.items`; value path
   `$.amount`, group by `$.currency`, missing values error.
4. Stop run: map an input such as `totals` from Summarize items `$`.

The summary contains EUR count 2/sum 20 and USD count 1/sum 9. Amounts arrive as
numbers, so this example needs no conversion expression.

Malformed-file errors tell you what to correct and include a row, column or
position when available. Size errors tell you to split the file. Run details
retain this diagnostic after reload without echoing file content; the one
exception is a missing Excel sheet, below, which lists the workbook's sheet
names so you can pick the right one.

## Read Excel workbooks

Choose **Excel** in Read file's Setup. The step reads one sheet of an `.xlsx`
workbook into the same rows CSV gives: one object per row under the header,
keyed by the header's names.

- **Sheet:** the sheet's name, shown as the tab under the preview grid. Leave it
  empty to read the first visible sheet. Names match as Excel matches them,
  ignoring case.
- **Header row:** the row with the column names, row 1 by default. Rows above
  it are skipped, so a title or a logo above the table is fine.
- **Convert numbers and booleans:** on by default, number and TRUE/FALSE cells
  keep their type and text cells stay text, even when they look like numbers.
  Off gives every cell as text, the way Excel's own CSV export would.

How cells read:

| In the workbook                              | In the rows                                         |
| -------------------------------------------- | --------------------------------------------------- |
| Numbers, TRUE/FALSE                          | Numbers and booleans (integers past 2⁵³ stay text) |
| Dates, times, date and time                  | `2026-10-19`, `09:30:00`, `2026-10-19T09:30:00.000Z` |
| Formulas                                     | Their last calculated value; nothing is evaluated  |
| Merged cells                                 | Every cell of the area reads the top-left value    |
| Rich text                                    | Plain text                                          |
| Empty cells / empty rows / trailing columns  | Empty text / skipped / dropped                      |

Headers follow the CSV rule: every column with data needs a nonblank, unique
name. A blank header between named columns, or data under no header, fails
with the column number. A title merged across the columns above the table
repeats in every column it covers, so reading it as the header fails and says
so: set **Header row** to the row with the column names.

How it works: the worker opens the workbook's zip directory before inflating
anything and refuses a workbook with more than 1,000 parts or 100 MB
uncompressed, then holds the same limits while it reads, so a "zip bomb" fails
fast without using memory. It reads at most 256 sheets and 1,000,000 cells in
one step. A cell reads up to 32,767 characters, Excel's limit, counted after
escapes such as `_x000D_` become their characters. Legacy `.xls`, macro-enabled
`.xlsm`, password-protected, OpenDocument and damaged files fail with a hint to
save the file as Excel Workbook (`.xlsx`); so does the rare workbook whose parts
are saved as UTF-16 rather than UTF-8. External links and embedded objects are
ignored and never fetched.

The editor never opens the file itself. After you test the step, Setup shows
the first rows it read in a small grid, the header row lit. If the sheet name
doesn't exist, the test fails and lists the workbook's sheet names (up to 20);
Setup shows them as tabs beside yours, and choosing one fills the name.

### Example: send a filtered sales sheet back as Excel

A workbook has a **Q2 2026** sheet with a title in row 1 and this table from
row 3: `region`, `city`, `sales`, `paid`.

**Read file → Filter items → Create file**

1. Read file: Excel, Sheet `Q2 2026`, Header row `3`. Upload the workbook on
   Inputs.
2. Filter items: map `items` from Read file `$`; path `$.paid`, equals boolean
   `true`.
3. Create file: Excel, map Data from Filter items `$.items`, columns `region`,
   `city`, `sales`, and name the tab `Paid orders`.

The new workbook opens with a bold, frozen header and the paid rows, numbers
still numbers. Map its `file` output to an HTTP multipart part or an email
attachment to send it on.

## Upload and finalize

Use the existing authenticated workspace artifact API. Upload/finalize requires
`artifact:upload`, with normal cookie-session/CSRF handling; an automation token
is not an upload credential. Viewers cannot upload. Files are shared within the
workspace, not private to the person who selected them.

1. Compute the exact file length and lowercase hexadecimal SHA-256.
2. Begin with `POST /v1/workspaces/:workspaceId/artifacts/uploads`, an
   `Idempotency-Key` and `{ byteLength, mediaType, sha256 }`. Keep that key and
   metadata unchanged while recovering this reservation.
3. PUT the unchanged file to the returned upload URL using its required headers.
   Browser-owned headers such as Content-Length come from the browser. Never send
   Pertexo's cookie or API token to storage. A signed URL is a short-lived bearer
   credential; never save it in a workflow or paste it into logs.
4. Finalize with an empty JSON body at
   `POST /v1/workspaces/:workspaceId/artifacts/:artifactId/finalize`. Only an
   `available` response is attachable. PUT success alone is insufficient.

If finalization's reply is lost, read metadata or repeat finalization for the same
ID. Do not create a second upload merely because a reply was uncertain. Pending
reservations expire after 15 minutes; retries cannot extend that deadline.

## Send a raw file body

In the editor, choose an HTTP Request using POST, PUT, PATCH or DELETE, open
**Inputs → Raw body → Upload body file**. Choose the file and wait for **File ready**.
**Use file as body** (or **Replace body with file**) inserts one undoable mapping.
Save before relying on retention. Remove that body mapping or undo to clear it;
replacing it does not erase workspace files.

The body value uses the same descriptor that HTTP artifact responses already emit:

```json
{
  "kind": "artifact",
  "artifactId": "11111111-1111-4111-8111-111111111111",
  "byteLength": 4,
  "mediaType": "application/octet-stream",
  "sha256": "REPLACE_WITH_THE_FINALIZED_FILE_SHA256"
}
```

Use real finalized metadata, not the illustrative ID/hash above. A literal `body`
mapping stores that descriptor. To supply a different file per run, place the
same descriptor under `file` in the run's JSON input and map HTTP `body` from run
input `$.file`. To forward an earlier HTTP response file, map from that step's
`$.body`. The earlier artifact must also fit the request's 10 MiB ceiling.

POST, PUT, PATCH and DELETE may carry a body. GET/HEAD reject bodies. The artifact
MIME type becomes Content-Type unless an explicit permitted header supplies one.
Existing inline `{ "encoding": "utf8", "value": "..." }` and base64 bodies keep
their behavior. For a form with several fields, use multipart below; parsing is an explicit Read file step.

## Send multipart form uploads

Choose an HTTP Request using POST, PUT, PATCH or DELETE, then **Inputs → Form
parts**. Add text and file parts in the order the destination expects. Each
part has a field name, its usual Value/Run input/Step output/Expression mapping,
and optional filename and content type. Use **Move part up/down** from the
keyboard or pointer to reorder without losing its value. Duplicate field names
are allowed and keep their order.

For an API that expects an invoice and a description:

| Part          | Kind | Value                                                                 | Optional metadata                                                 |
| ------------- | ---- | --------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `description` | Text | `March invoice` or run input `$.description`                          | Default `text/plain; charset=utf-8`, no filename                  |
| `document`    | File | Upload part file, run input `$.file`, or prior HTTP response `$.body` | Deliberate filename `invoice.pdf`, content type `application/pdf` |

A file part defaults to filename `file` and its verified media type. A filename
is also permitted on a text part if the receiving API requires it. Only the
filename you explicitly enter is saved; the original local filename is not
copied automatically. Changing content type changes metadata, never the bytes.
Names/filenames refuse control characters, filenames refuse paths, and content
types cannot contain header line breaks.

Pertexo generates the random boundary and the outer Content-Type. Remove any
custom Content-Type from the step **and its connection**; a conflict fails
clearly before sending. GET/HEAD refuse bodies. Existing raw UTF-8/base64/file
bodies keep their behavior. Switching body mode or replacing a populated mapping
asks before discarding it; Cancel keeps it, Undo restores a completed change.
Incomplete parts prevent save/publish. The known-data estimate excludes form
headers and dynamically mapped values; the worker checks the exact final body.

All headers, boundaries and closing framing count toward 1 MB. For example, a
1 MB file cannot be sent as one multipart part even if its stored reference is
valid. Use a smaller file or split uploads only when the destination supports
that. Pertexo does not automatically split a multipart request.

## Attach files to an email

**Send email** can attach up to 10 files produced earlier in the run. Open the
step's **Inputs**: **Attachments** sits under the message. **Attach a file**
lists the file outputs of steps linked right before this one, such as Create
file's `file` or an HTTP response saved as a file, and the run input's `file`.
A workflow started by a [Form](forms.md#file-questions) lists each file
question instead, as **all files from** its label: that maps the whole answer
(`$.values.<name>`), so every uploaded file goes out under the name it was
uploaded with. A Request input linked right before the email offers its file
questions the same way, from its output. **Another source…** takes a step
output path, run input path, variable or expression, as other inputs do.
**Upload a file** attaches the same fixed file to every email, such as terms or
a price list.

Each attachment is a chip with its type, name and size. The pencil opens **Name
in the email**; leave it empty and the file is named from its stored type,
`attachment.csv`, or `attachment-2.pdf` when there are several. Names lose path
separators and control characters and stay within 255 bytes with the extension
kept. The content type is the file's stored media type, never sniffed. The meter
under the list fills toward the limit with the sizes it already knows (uploaded
files); files from earlier steps are measured when the run sends them.

### How it works

The step has one optional `attachments` input: a list of
`{ "file": <file reference>, "filename": "optional name" }`. The editor writes
it for you. A step that already returns such a list, for example Code, can be
mapped to it as a whole. Email steps without attachments send exactly what they
did before.

Before anything is sent, the worker counts the files, adds up their size after
base64 encoding (as email providers measure it), then reads each one through the
same verified workspace read as Read file and multipart. A missing, unfinished
or other-workspace file fails as the usual file problem; more than 10 files
fails as too many attachments and more than 6 MB of files as attachments too
large. Nothing is sent in those cases. The 6 MB leaves room for the message
inside the 10 MB request ceiling every outgoing file body shares. The message
and its files go through worker scratch to Resend as one request.

For example, to email the weekly report:

1. **Create file**: CSV with the columns `week` and `total`.
2. **Send email**: map To, Subject and Text, then **Attach a file → Weekly
   report → file** and name it `weekly-report.csv`.

The saved mapping evaluates to:

```json
[
  {
    "file": { "kind": "artifact", "artifactId": "…", "byteLength": 1234, "mediaType": "text/csv; charset=utf-8", "sha256": "…" },
    "filename": "weekly-report.csv"
  }
]
```

The step's output names what it sent, never the contents:
`{ "emailId": "…", "attachments": [{ "filename": "weekly-report.csv", "mediaType": "text/csv; charset=utf-8", "byteLength": 1234 }] }`.
Run detail shows those files as the same chips. Sending doesn't copy a file or
extend its storage; the run that references it keeps it, as for any step input.
A retry reuses the step's provider idempotency key with byte-identical content,
so Resend delivers one email. HTML bodies, several recipients, inline images and
files from URLs that aren't stored files are not supported.

## What is checked and what can repeat

Every consumer uses the existing workspace-bound worker read. It requires an
available artifact and matches ID, byte length, media type and SHA-256, then
verifies the complete bounded bytes. Foreign, missing, pending, deleting,
preview-owned or tampered files cannot become permanent authoring references.
An HTTP step dispatches only after all its file reads and multipart preflight
succeed.

Files remain opaque until an explicit Read file step. Pertexo does not scan for
viruses, render or execute uploads, and only Read file's Excel format
decompresses, within the limits above; a MIME label is not a safety
guarantee. Downloads stay attachments. Read file is safe to repeat and existing
same-run automatic retries handle temporary storage failures. A malformed file
needs corrected content in a new run.

HTTP uploads are unsafe external operations: a failed response or lost
connection may still have taken effect. Existing unknown-outcome attention and
explicit recovery acknowledgements apply unchanged. This release adds no special
Read file recovery exception and does not relax F09's artifact/reused-prefix
restrictions. See [failure paths and recovery](../feature-plans/09-failure-paths-and-recovery.md).

## Files from forms and input requests

A [form or Request input file question](forms.md#file-questions) uploads through
the same begin → direct upload → finalize transfer, bound to that response. The
run receives each file as `{ "file": <file reference>, "filename": "…" }`, so
`$.values.<field>[0].file` maps straight into Read file. Unlike editor uploads,
responder files are checked against the field's kinds and size, and their first
bytes must match their extension.

## How long files stay

An unreferenced finalized upload has the existing 30-day deadline; a form or
Request input upload that was never sent has one day, or one hour through a
public form link. A retained
draft, published version, input-case payload, execution fact or answered input
request protects its file.
Archiving a workflow keeps these references. Old input-case payloads stop keeping
files when the existing retention reaper removes them. Preview outputs keep
preview lifetimes and cannot be promoted into permanent workflow/run ownership
by copying their IDs.

Clearing/replacing an attachment changes its owner; it does not immediately erase
shared bytes. After the final retained reference disappears, expired files become
eligible for cleanup. Abandoned pending uploads also expire normally. Storage
remains charged until physical deletion succeeds. Workspace purge still erases
its files through the existing deletion process.

Exports keep literal file descriptors, not file bytes. Duplicating within the
same workspace can reuse them. To import into another workspace, upload there
and replace the literal descriptors; Pertexo will not grant access through a
foreign ID or silently copy the file.

Save an attachment before relying on its retention. Unsaved browser state is not
a durable reference. If a file is unavailable, re-upload and attach its finalized
reference; do not substitute a signed download URL for the descriptor.
