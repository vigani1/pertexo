Pertexo web · redesign plan Sep 2026

Weft.

A redesign of every Pertexo screen. Runs become threads, the orb becomes the product's living core, and glass is only used for things that float.

Pertexere is Latin for “to weave through, to finish”. The new visual language takes that literally. Your cyan, lavender and graphite palette, the 3D orb, the aurora edge and the glass panels all stay, but each one gets a single job. All data in the mockups is example data. The tags show whether a feature works with today's backend.

01

Five materials, one rule each.

The current app puts the same glass card on everything, so nothing stands out. Weft limits the palette to five materials and gives each one a single meaning. People learn them once and can read any screen after that.

Thread

A run is a thread moving through time. It ends in a knot when it succeeds, frays when it fails, coils while it waits, and grows while it runs.

Every status in the app uses a thread glyph.

Loom

The loom is time laid out sideways, with one lane per workflow. It powers Home, the Loom view in Runs, and the step timeline on each run page.

Charts come from real run times, never made-up metrics.

Core

The 3D particle orb becomes the heartbeat. Its energy follows the amount of live work, and its colour follows the state of a run.

At most one large animated Core per screen.
Lens

Lens

Glass is only used for things that float above the page: the spine, the command bar, the inspector, dialogs, menus and toasts.

Page content is never glass.
running

Live edge

The aurora becomes a light that runs along an edge, but only while work is actually happening: a running step, a publish, a test.

If nothing is happening, nothing moves.

Three directions we tried

Console

Top tabs, KPI tiles and dense tables. Fast to build and easy to scan, but it's the layout every AI-generated SaaS app already has, and it has nowhere to put the orb or the aurora.

Rejected: generic

Orbital

Everything circles the orb: workflows as planets, runs as moons. Very memorable. But it's slow to scan, hard to use with a keyboard, and falls apart once a workspace has 40 workflows.

Rejected: doesn't scale

Weft (chosen)

A slim spine for navigation. The loom is the hero, and live threads feed into the Core. Detail views keep dense lists, but they're drawn as threads rather than boxes.

Chosen
02

What's wrong today.

This comes from reading all 20 routes, the style sheet, the API contracts and the architecture notes. The agents made the logic solid, but the problems below are why the app still doesn't feel like a product.

Everything is the same glass box

GlassSection is used for page headers, lists, forms and settings alike. The inspector stacks four bordered boxes inside each other. When every surface is glass, glass stops meaning anything.

Status has no language

In the run detail header a succeeded run looks the same as a failed one. Failed saves are lavender. Enabled alert destinations are grey while disabled ones are lavender. There are no success or warning colours at all.

The UI talks like the database

Full UUIDs appear on every workflow row. The palette shows core.http.request@1. Buttons say “Retry exact command”, “Dismiss attempt”, “bounded workspace listing”. Error codes like code · path are shown raw.

Results are invisible

Run detail never shows a step's output, error text or timing, and the steps can't be clicked. A node test hides both its inline output and the list of validation issues.

The editor fights the builder

The palette shows raw keys with no search and no drag. New nodes can land off-screen. Edges can't be deleted. Port names are only in a tooltip. Every edit needs an Apply click. Publish quietly requires Validate first.

Navigation is scattered

Settings live in three different places. The workflow settings page never shows the workflow's name. Switching workspace means leaving to another page. Every browser tab is titled “Pertexo”, and the shell reloads on every navigation.

Feedback is missing or overdone

There are no toasts. Creating a workflow doesn't open it. Cancelling a run happens without confirmation. Meanwhile trivial actions get long dialogs full of idempotency language.

The signature effects are wasted

The orb only appears as a 16px spinner in one button. The aurora wraps whole lists while they load, rotating a 150vmax layer. The background glows never move.

Durations: 120 ms for small changes, 240 ms for panels, 600 ms for reveals. One easing everywhere: cubic-bezier(.2,.7,.2,1), called “unspool”. With reduced motion turned on, the glyphs stay still, the Core renders a single frame, and the growing threads jump straight to their current length.

The Core: engineering budget

  • A single <Core state size energy> component. It ports the legacy Three.js shader to plain WebGL2 point sprites (about 3 KB, no Three.js) and falls back to Canvas 2D. It's lazy-loaded, so it adds nothing to the first load of any route.
  • States: idle, live, waiting, failed and succeeded change the colours and motion. energy (0–1) scales the wave amplitude from the live-run count.
  • At most one large animated Core per screen. Small Cores (the spine) use 150 particles and pause while the tab is hidden. Offscreen Cores stop through IntersectionObserver. Device pixel ratio is capped at 1.75. Budget: under 2 ms per frame at 1,500 particles on an M1.
  • The existing CSS LoadingOrb stays as the inline spinner inside buttons.
04

Loading, validation & alerts.

These are the moments people see most often, so they get the same craft as the Loom. Everything here is live: replay the demos, type into the form, fire the notifications.

Loading: honest, and never a blank screen

Validation: say what's wrong and how to fix it

  • Copy rules: every message names the field, says what's wrong, and how to fix it (“That's missing the end of the domain, like .dev”). Never “Invalid input”. Never an error code on its own.
  • Long forms (connection create, invites) add a one-line summary at the top that links to each problem. Short forms don't.
  • JSON and expression fields underline the exact spot with a salmon wavy line and give line and column (“Missing a closing brace at line 3, column 14”). Expressions preview their result live against the last test.
  • Accessibility: aria-invalid and aria-describedby on every field, one polite live region per form, focus on the first invalid field after submit. Under reduced motion the knot and fray still appear, just without animating.

Notifications: toasts with a thread for a timer

Workflows

Toast lens

  • Bottom-right glass lenses, at most 3 (older ones fold into “+2 more”). Each has a status glyph, one sentence, an optional single action, and a close button.
  • The timer is a thread that shortens toward its knot. Hover or keyboard focus pauses it. Success 4 s, info 6 s, Undo 8 s (the thread is the undo window). Errors never time out.
  • Progress becomes result in place: “Publishing v8…” with the live edge turns into “v8 is live” with a knot, so it's one toast, not two.
  • Screen readers: success and info are role="status" (polite); errors are role="alert".

What triggers one

  • Every create, rename, revoke, invite and role change (all silent today). Deleting a node or mapping gives “Step deleted · Undo”.
  • Run finished elsewhere: for runs you started in this browser, when the run page isn't open. Success is a short toast. Failure persists with Open run.
  • Rate limited: “Too many publishes in a minute. Try again in 0:24”, counting down from Retry-After.
  • Not a toast: states that last (offline, read-only maintenance, reconnecting live updates, workspace pending deletion) are banners under the breadcrumb. When a new failure appears, the spine Core flickers salmon once and the Runs count rolls to its new number.
  • There's no notification inbox in the backend. A “Recent” list in the account menu can show this session's toasts (browser memory only). A real inbox is a later backend slice. needs API

When things go wrong

Not-found is split into three cases, because today they share misleading copy: no such address, no such workflow or run (“doesn't exist, or you don't have access”, to match the API's 404 policy), and workspace unavailable. Every error page keeps the shell, so people can navigate away without reloading.

Layout

  • A full-bleed stage. The Core sits at about a third of the width, with threads flowing into it from the edges: the literal “weave” moment. It pauses offscreen and renders a single frame under reduced motion.
  • The form is a glass lens docked on the right at 404px, the one correct use of glass here, since it floats over the Core. Below 900px the Core shrinks to a 180px band above the form and the threads turn off.
  • Bottom-left: a tagline and three honest product facts. The “PERTEXO / CONTROL PLANE” eyebrow and the cookie disclaimer go.

Sign in

  • Social providers come first when GET /v1/auth/capabilities lists them, then “or with email”. Password gets show/hide, and “Forgot?” sits in the label row. API ready
  • Link parameters (verified, emailChanged, emailChangePending, error=verification_invalid, link_reauthenticate, migration_*) become a status line inside the lens. An expired verification link offers “Send a new link”.
  • auth.email_not_verified flips the lens to a “Verify your email” state with Resend (60-second cooldown) and “Use another email”.
  • A 429 disables the button and shows a live countdown from Retry-After. While a request is in flight, the lens shows the live edge and the button shows the mini orb.
  • When no sign-in methods are available, a Retry button appears (today there's none). Links use the router instead of full page reloads. bug fix

Sign up · recovery · reset

  • Sign up: name, email and password, with a live requirement meter using password.minimumLength. On success the lens turns into “Check your inbox” showing the address, Resend with a cooldown, and “Wrong address? Start over”. The second resend form that's always visible today is removed.
  • Forgot: one field, then a neutral confirmation (“If an account exists…”) plus a resend cooldown.
  • Reset: a missing token shows “This link is incomplete” with Request a new one. The form is new + confirm with the meter. Success says that other sessions were signed out, then offers Sign in.

Migrate · sign out

  • Migrate: a three-step stepper (Choose new method → Confirm old account → Done), one sentence per step. After step 1, the 5-minute window shows as a visible countdown.
  • Sign out: the Core fades down with “Signing out…”. If it fails, show “We couldn't confirm sign-out” with Retry.

Layout

  • Header: the workspace name as the title. A mono status line gives exact live counts, failures in 24 hours and the server's “as of” time. Actions: Search, which opens the ⌘K palette, and New workflow (if workflow:create), which opens the Workflows list's New workflow lens (workflows?create=true).

Window options: 1h, 6h, 24h, 7d. Each lane label carries the workflow's exact total for the window, and a caption states the window's exact total. Hovering a thread shows a small lens with the run summary; clicking opens the run.
  • Below: “Needs attention” on the left and “Recently changed” on the right.

Data

  • Loom threads: GET /runs?createdAtFrom=…, paging up to 300 runs, plus one page per active status created before the window so long runs still reach the Core. API ready
  • Loom caption and lane totals: GET /run-statistics?window=1h|6h|24h|7d&breakdown=workflow. When the drawing stops at 300, the caption says so next to the exact total. API ready
  • Counts: GET /run-statistics?window=24h gives exact queued, running and waiting counts and failures in 24h from one snapshot. The spine's live count shares the same read. API ready (ADR 044)
  • A 30-day window stays out: ADR 044 keeps windows well inside run-summary retention and the query budget.
  • Recently changed: GET /workflows?order=updated_desc&limit=6.

Needs attention (all derived, no new API)

  • Failed, timed-out and unknown runs, grouped by workflow (“failed twice in the last hour”), with Open run.
  • Workflows with activationStatus of degraded or error, with Check triggers.
  • Connections in reauthorization_required, with Reconnect (only if connection:manage).
  • Disabled alert destinations, with Review.
  • When everything is fine: a single knotted thread with “All clear. Nothing needs you.”

New workspace & states

  • New workspace: the Loom is replaced by a “First thread” checklist: create a workflow, publish, run it, add a connection, set a failure alert, invite a teammate. Every step is derived from real data, and each finished step ties a knot along one thread. Each step links to where it's done: the New workflow lens, the latest workflow's Build tab (or Workflows), the Add connection lens, Alerts and the Invite lens. Steps the current role can't check are hidden (for example, invites need member:read and alert destinations need workflow:update).
  • Loading: skeleton threads shimmer along the lanes. Each block loads and fails independently, as it does today.
  • Replaces: three different card styles, “No items yet”, and run rows that show ID fragments.

07

Backend gaps the design needs.

Every item below is designed with a fallback that works on today's API and never shows invented data. The endpoints complete them. Each contract is written in the backend's existing style, checked against the backend plan, the contracts package and ADRs 004–046. Where a gap goes beyond an existing ADR, the table says so, because the repo rules require the ADR before the code. Rows marked Delivered have shipped.

House rules every new endpoint follows

  • Paths are scoped to a workspace: /v1/workspaces/:workspaceId/…. Commands are a POST to a verb (/archive, /rename, /cancel, /revoke, /members/:userId/role). PUT replaces a sub-document (/draft, /secret, /status, /failure-notification-policy). PATCH renames: the workspace and the signed-in person's own display name.
  • Contract first: a Zod request and response schema in packages/contracts/src/http/*, OpenAPI artifacts regenerated (contracts:check catches drift), and the browser schema subpath reviewed into the web import allowlist.
  • Commands take an Idempotency-Key and an expected* revision in the body, or a strong If-Match for draft representations (ADR 011). They answer with replayed, and conflicts return a *.revision_conflict problem carrying the current revision.
  • Lists use limit ≤ 100, an opaque after / nextCursor, deterministic (created_at, id) order and allowlisted filters. Name filters are prefix filters named like the existing workflowNamePrefix.
  • Errors use the single RFC 9457 problem shape with catalog codes (domain.reason). A 404 hides resources the caller isn't allowed to see.
  • Every route declares a capability (run:read, member:manage…) and a rate-limit class (authenticated_read, ordinary_mutation…). It returns a purpose-built read model, and says what happens once ADR 013's retention window has passed (attempts and events are kept 30 days, run summaries 90, previews 7).

08

Build order.

Six phases. Each one ships on its own and leaves the app better than before. The foundations have to come first, because every later screen uses them.

1 · Foundations

Tokens and the Bricolage font; the primitives listed above; the Core component (WebGL2 + Canvas 2D fallback, within budget); live edge v2 (@property); a single status.ts map and error-copy map; the feedback kit (boot Core, spooling skeletons, field threads, toast lens with thread timer, error pages); the nested workspace layout route and document titles.

2 · Shell

Spine, breadcrumb switcher, ⌘K command lens, banners, toasts, the mobile bottom bar, and Account moved into the shell. Capability-aware hiding plus the Forbidden page.

3 · Operate

Runs list with ThreadBars and fixed filters; run detail with the Thread, Graph and Events views, the step lens and artifact outputs; Home with the Loom and Needs attention.

4 · Build

Workflows list with pattern glyphs and starters; the editor rework (add-step lens, edge interactions, inspector tabs, live apply, issues lens, publish weave-in, run lens); the workflow tabs.

5 · Admin & entry

Connections for all three providers; Team with the roles matrix; Alerts; workspace Settings; the sign-in family, invitation and picker on the Core stage.

6 · API-gated

Switch on each needs API surface as its endpoint lands. P1 first: attempts and outputs, run input. Stats have landed (ADR 044).

Every surface must meet these before it ships

  • Designed states: loading, empty, error, stale, forbidden and read-only. A keyboard path through every action. Works at 390px. Reduced motion (static glyphs, a still Core). Forced colours (the live edge becomes a Highlight outline).
  • No raw IDs, enum values or error codes outside a Details area. Every destructive action has either a confirmation or an Undo.
  • Performance: at most one large animated Core per screen, paused when offscreen or when the tab is hidden. No layers larger than the viewport being animated.
  • Unit tests and the mocked Chromium journeys updated to match the new copy and structure. Screenshots reviewed at 1280px and 390px.
  • Overrides to apps/web/ARCHITECTURE.md recorded in the same change: the display font, the Core (instead of the deferred Orb Wave), the spine (instead of the 13.5rem sidebar), workflow tabs, and Home as the landing page.
